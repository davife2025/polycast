# Env setup changelog

Scope: a real bug fix in `apps/api`, new per-app env templates, and a new
`SETUP.md` walking through provisioning every credential the monorepo needs.

## Bug fixed: `apps/api` never actually loaded `.env` files

Every session up to now, `apps/api/.env.example` existed and looked
correct — but nothing in `apps/api` ever called `dotenv.config()` or
imported `dotenv/config`. Creating `apps/api/.env` and filling it in
would have silently done nothing; the service would have kept using
`process.env` defaults regardless of what was in the file.

Fixed by adding `dotenv` as a real dependency and importing `dotenv/config`
as the literal first line of `src/index.ts` — this matters because with
`"module": "commonjs"` in `tsconfig.json`, imports execute top-to-bottom
in the order written, so this has to run before `lib/chain.ts`,
`lib/supabase.ts`, and the indexer modules (all of which read
`process.env` at module-load time) get imported.

**Verified, not just assumed fixed:** created a real `apps/api/.env` with
`PORT=4099` and confirmed the server actually logged
`Server listening at http://0.0.0.0:4099` — proof the file was
read, not just present.

## New: per-app env templates

Previously only the root `.env.example` documented every variable, but
nothing actually loads from the repo root — Next.js reads `.env.local`
from `apps/web/` specifically, and (now that the bug above is fixed)
`apps/api` reads `.env` from `apps/api/`. Added:

- `apps/web/.env.local.example`
- `apps/api/.env.example`

The root `.env.example` now has a header pointing to these, so it's
clearly a reference rather than something to copy directly.

## New: `SETUP.md`

Step-by-step walkthrough for provisioning every credential from scratch:

1. **Supabase** — create a project, run `packages/supabase/schema.sql` in
   the SQL editor, where to find the URL/anon key/service role key, and
   which file each goes in (with an explicit warning that the service
   role key must never reach `apps/web` or the browser).
2. **A testnet wallet** — explicitly recommends a fresh, disposable key
   never used for real funds on any network, how to add Coston2 to a
   wallet, and the faucet link.
3. **Deploying the contracts** — running `npm run deploy:coston2` and
   copying its printed output (all four contract addresses, plus how to
   populate `RESOLVER_TYPE_MAP` with the deployed `ManualResolver`'s
   address) into the right files.
4. **Running everything** — `npm install && npm run dev` from the root.

Root `README.md` updated to point here instead of the old (and, per the
bug above, partially incorrect) getting-started snippet.

## What was verified, not just written

- The dotenv fix was verified with a real running process reading a real
  `.env` file, not assumed correct because it compiled.
- `apps/api` still passes `tsc --noEmit` after the change.
- `apps/web` still builds clean (unaffected by this change, re-verified
  after the shared workspace reinstall).

## Note on what wasn't (and can't be) provided

No actual Supabase project, wallet key, or deployed contract addresses
are included here — those all require accounts only you control, and a
private key or service role key should never be generated by, or shared
with, anyone else, testnet or not. `SETUP.md` tells you exactly where to
get each one and exactly which file it goes in.
